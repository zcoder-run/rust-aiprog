# AIProg Overview

AIProg is a Rust runtime for executing constrained Lua programs against APIs selected by a host application. Instead of asking a model to choose one tool at a time, the host can give it a description of the available APIs and ask it to write a small program. The program can combine calls, branch on results, and transform data before returning a value. A model is optional: AIProg can execute the same program when it is written by a person or generated by another system.

This specification is the starting point for the architecture. The linked specifications describe individual components and their contracts in more detail. See the [project README](../../README.md) for positioning and the [crate Rust API overview](../../docs/rustdoc/lib.md) for public entry points.

## Architecture at a glance

| Layer                 | Key concepts                                                    | Role                                                                                                               |
| --------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Host application      | `AipRegistry`, `ScriptEngine`, `RunningContext`                 | Selects the functions scripts may call, configures the runtime, and supplies per-execution state and policies.     |
| Script authoring      | `ScriptEngine::generate_doc`, Lua                               | Describes the selected API to a person or model so they can write a script against it.                             |
| Lua execution         | `RunningEngine`, `LuaRuntimePolicy`, `NativeFunctionSet`        | Owns the Lua session and runs scripts with the configured libraries, handlers, and native functions.               |
| Rust handler boundary | `AipParams`, `HandlerCallContext`, `HandlerResult`, `AipOutput` | Converts a Lua argument into typed Rust input, runs host code, and converts the result back to Lua.                |
| Host result           | `RunOutcome`                                                    | Returns the script result or script error alongside the recovered execution context when context handoff succeeds. |

The central distinction is between **what a script can call**, **what Lua itself can do**, and **what host state a handler can access**. The registry, runtime policy, and running context control those concerns separately.

## Configure and run a script

### 1. Select the callable API

`AipRegistry` is an immutable collection of handler definitions. Each definition includes a dotted Lua path, sync or async dispatch, schemas, and a factory for binding the handler to a session. A registry definition is not a live Lua function and does not carry per-execution context.

Start with `AipRegistry::from_empty()` for an explicitly selected API, or use `AipRegistry::from_aip_modules()` to obtain the built-in registry. `AipRegistryBuilder` can add modules and custom handlers. Use `select` or `exclude` to derive a narrower registry, and use `to_builder` to extend it without mutating the original. `RegistrySelectionOptions` can make unmatched patterns an error, which helps catch configuration mistakes.

References: [Registry Rust API overview](../../docs/rustdoc/registry/mod.md) and [registry architecture](spec-engine.md#registry-architecture).

### 2. Build the engine and supply context

`ScriptEngine::builder()` combines the registry with Lua runtime policy and any explicitly installed native functions. The resulting `ScriptEngine` is reusable configuration; it does not own a live Lua VM or the caller's `RunningContext`.

`RunningContext` is an owned Rust type map. It holds at most one value of each concrete type, and those values are not exposed directly as Lua globals. For example, `DirContext` governs built-in file access, while `AiContext` can provide a GenAI client, model aliases, and a default model for AI-backed handlers. The engine supplies a current-directory `DirContext` when none is provided; it does not supply an `AiContext`.

References: [Execution with context](../../docs/rustdoc/lib.md#execution-with-context), [running context architecture](spec-engine.md#running-context), and [Lua runtime policy](spec-lua-policy.md).

### 3. Generate the API reference when needed

`ScriptEngine::generate_doc()` produces Markdown with TypeScript-like handler signatures derived from registered handler metadata and JSON schemas. The signatures describe the Lua API; scripts are still written in Lua. Generate the reference from the engine configured for the task so script authors are not told to call handlers that will not be installed. Documentation describes capabilities; it does not grant them or replace runtime policy.

References: [Generated API example](../../examples/.out/c03-doc.md), [schema reference helpers](../../docs/rustdoc/schema_ref/mod.md), and [model-authored script example](../../examples/c05-genai.rs).

### 4. Execute and recover the result

Use `ScriptEngine::exec(script, context).await` for a one-shot execution in a fresh Lua session. Use `ScriptEngine::start()` to create a `RunningEngine` when sequential scripts must share Lua state. Each `RunningEngine::exec` call takes its own owned context, makes it available to handlers for that execution, and takes it back out when the execution finishes. Lua globals persist within a session but are not shared across sessions.

The outer execution result reports engine lifecycle failures. If execution returns a `RunOutcome`, `outcome.result` contains either the script value, represented as JSON at the host boundary, or a script error. The recovered context remains available in either case. `RunOutcome::into_parts()` separates the two.

```rust
use aiprog::{AipRegistry, RunningContext, ScriptEngine};

async fn run() -> Result<(), Box<dyn std::error::Error>> {
	let engine = ScriptEngine::builder()
		.with_registry(AipRegistry::from_empty())
		.build()?;

	let outcome = engine
		.exec("return { message = 'hello' }", RunningContext::default())
		.await?;

	let (result, _context) = outcome.into_parts();
	assert_eq!(result?, serde_json::json!({ "message": "hello" }));
	Ok(())
}
```

References: [Execution lifecycle](spec-engine.md#execution-lifecycle), [error and context recovery](spec-engine.md#error-and-context-recovery), and [isolation guarantees](spec-engine.md#isolation-guarantees).

## How Lua calls Rust

Built-in handlers use `aip.<module>.<function>` paths. Hosts can register their own namespaces. By convention, a handler accepts one Lua table with named fields. It returns a single value, which may be a scalar, a list, or a structured table, or it raises a Lua error. Expected domain outcomes can be ordinary return values; for example, a completed HTTP exchange can return `success = false` without raising an error.

1. `AipFromLua` converts the Lua argument into an `AipParams` value. Custom conversions can use `LuaExt::x_try_get_*` to distinguish optional fields from present fields of the wrong type.
2. The handler runs synchronously or asynchronously. It can use `HandlerCallContext::with` or `with_mut` for short, scoped access to typed state. It should not retain the call context after its work is complete.
3. On success, `AipIntoLua` converts the `AipOutput` directly to a Lua value. On failure, `HandlerResult` carries a handler error that is surfaced to Lua. JSON schema describes the boundary for documentation and tooling; it does not replace Lua conversion or handler validation.

Register typed functions manually with `register_sync` or `register_async`, or use `#[aip_handler]` and `register_handler!` for generated metadata and registration support. Group related handlers in an `AipModule`.

References: [Handler and registry scheme](spec-handler-scheme.md), [Lua signature conventions](spec-aip-api-lua-signature-patterns.md), [Rust implementation patterns](spec-aip-api-rust-impl.md), [Lua and JSON conversion helpers](spec-lua-ext.md), and [custom handler example](../../examples/c02-custom.rs).

## Built-in capabilities and isolation

The [built-in module registry](../../src/modules/mod.rs) assembles handlers for areas such as JSON, files, HTTP, HTML, Markdown, text, time, and refinement. Built-ins follow the same handler contract as application-defined functions. For example, the web handlers expose a Lua-facing request and response shape while a separate [WebClient abstraction](spec-webc.md) handles HTTP.

For restricted execution, review all layers together:

- **Registry and native functions:** Expose only the operations the script needs. Registry selection does not filter separately installed native functions.

- **Lua policy:** Review the enabled standard libraries independently of the registry. The runtime supports a Lua memory limit, but configured instruction limits and wall-clock timeouts are currently rejected as unsupported.

- **Host capabilities:** Supply explicit directory policies when current-directory access is too broad. Review what clients and state custom handlers expose, including network destinations or credentials where applicable.

- **Session lifetime:** Prefer a fresh session when scripts should not share globals. Session isolation does not undo side effects performed by a handler.

References: [Lua policy and sandbox specification](spec-lua-policy.md), [filesystem capabilities](../../docs/rustdoc/lib.md#filesystem-capabilities), and [current engine limitations](spec-engine.md#current-limitations).
